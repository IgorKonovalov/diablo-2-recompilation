(b) among the classes "that need no new session". The plan also says the classes are 0038's "unchanged", and in 0038 (b)

plan's Phase 1 bullet.

### The per-spec files

- One file per spec, named `<subsystem>-<spec>.md` (`monsters-ai-catalogue.md`, `sim-frame.md`).
- Columns: `#`, *Line* (the spec line at the recorded commit), *Section* (the nearest heading), *Claim* (a short excerpt,
  about 15 words), *Anchor* (the first anchor at or after the tag), *Class*, *Route or reason*, *Batch*, *Count*.
- One row per spec line that carries `[I]`; *Count* is the number of `[I]` on that line. A line whose tags fall in
  different classes is split into rows with the same *Line*, each with its own count.
- The row skeletons (line, section, excerpt, anchor, count) were generated by a script from the spec text; the class,
  route and batch are the architect's.
- The *Route* names the log family or run and the check, the recipe and logger, the second code path or table, the
  emulation boundary, or the `d-` reason, in about 25 words or fewer.
- Each file ends with **Totals by class**, summing to the front-matter `I`.
- **No value tier.** Plan 0038's T1–T3 tiers ranked the creation chain. Here every claim is simulation, so batches are
  ordered by claims per session (the owner's threshold) and then by size.

### Batches

- Ids by group: `S1`/`H1` monsters/ai; `S2`/`H2` skills; `S3`/`H3` quests; `S4`/`H4` items/economy, use, inventory and
  stats; `S5`/`H5` combat; `S6`/`H6` anim; `S7`/`H7` sim/frame, path, drlg/lifecycle and player/party. A letter suffix
  splits a group (`S1a`, `S1b`); an emulation batch ends in `e` (`S2e`).
- Caps, as 0038: a static batch holds at most 100 statements; a harness batch at most 60 statements and 20 sessions,
  one logger family.
- **Threshold (owner question 2):** a harness batch runs only if it raises at least 20 claims per session (statements ÷
  estimated sessions ≥ 20). A batch below it is listed with **deferred** in the batch list; its rows keep their class and
  batch id, so the review can merge it into a batch that passes.
- (d) rows have no batch (`–`).

## 2. The threshold and the harness batches

**No harness batch reaches 20 claims per session.** The 31 batches estimate 0.2 to 11 claims per session, about 2.8 on
average (705 statements over about 256 sessions; 699 as filed, six rows moved in at the review). The best are H1e (55 over 5) and H1b (45 over 5), both monsters/ai
catalogue rows by act. The reason is the same in every cluster: the simulation `[I]`s that need a run are one-off
branches, one monster, quest step or item state per scene, and no grouping by logger family puts 20 of them in one
session. Under the owner's threshold as written, **Phase 2 is empty and all 705 rows are (a-run, deferred) or (b,
deferred)**. The review is asked to rule on one of:

1. keep the threshold; Phase 2 does not run, and the 705 rows are recorded as deferred at Phase 1's close;
2. count **launches** under the runner library (ADR-0028: several cases per launch) instead of sessions. Helper `ai1`
   estimates a monsters/ai "bestiary tour" (logger rev 7, the S1b block checker, many `stage` cases per launch, one
   launch per act) at about 214 statements in about 12 launches, near the threshold; no other cluster made that
   estimate;
3. a separate sub-plan for the monsters/ai harness rows (plan 0066's open question; `ai1` recommends one for the
   harness part only, the static part fits Phase 1 as it is).
