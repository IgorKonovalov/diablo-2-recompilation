## Answer (summary)

- [I] **1. `UnitRelocate`'s death arm does not test `deadCol`.** For a monster (unit type 1, the jump table entry `0x00554B10`) the arm's only test of the dead state is `sub_0063EA40_MonIsDeathMode(unit)` at 0x00554B68, which holds for mode 0 and mode 12. When it holds, the arm calls `UNIT_CollUnmark(unit, 1)` (0x00554B78), sets pattern 5 (`0x00554B80`) and mask `0x8000` (`PATH_SetMarkMask`, 0x00554B8E). No call of `sub_004638A0_MonStats2FlagTest` lies in 0x00554B10–0x00554B93, and none of the arm's ten direct callees is a function holding one of the four direct `deadCol` tests of the image (below). So a monster with `deadCol` 1 that is relocated dead takes the same pattern-5 `0x8000` plus at its new place as one with `deadCol` 0 (after the case's moves of the path, 0x00554B18–0x00554B62). This differs from `SUnitCreate`'s arm (drlg/0005 Q7), which does test it (0x00555481). Callees' own callees are not followed. (0x00554B10–0x00554B93, 0x00554B68, fn:sub_00554A30_UnitRelocate@0x00554A30, fn:sub_0063EA40_MonIsDeathMode@0x0063EA40, `r70-flagtest-sites.txt`)
- [I] **2. `UNIT_CollUnmark(unit, f)`: `f` is "also unmark a unit whose live mark is already off".** The function switches on the unit type (0x00649574–0x00649589). **Players (type 0):** in mode 0 or 17 it returns 0 with nothing unmarked when `f` is 0, and unmarks when `f` is non-zero (0x006496B7–0x006496CB); in any other mode it unmarks whatever `f` is. **Monsters (type 1):** the same with modes 0 and 12 (0x006496AB–0x006496CB). **Objects (type 2):** unmarks when `HasCollision[mode]` (0x006219C0, `Objects` `+0x120 + mode`) is non-zero, whatever `f`; when it is 0, unmarks only if `f` is non-zero (0x00649611–0x0064961D). **Types 3 and above (and the other tail):** `f` is not read (0x0064958F). It returns 1 when it unmarked and 0 when it did not (0x00649752). Callers: `f` = 0 at 4 of 15 direct calls: `PathPlan` 0x00649B07 and 0x00649B25 (the second's result drives the tail's re-mark of a target, path/0005 T1) and the two of `sub_00622B50_UnitsLineBlocked`, 0x00622BC1 and 0x00622BD7; `f` = 1 at the other 11 (0x00460C9D, 0x004AEAE6, 0x00554AF0, 0x00554B78, 0x0055548D, 0x005554C2, 0x00649CBC, 0x00649F5F, 0x00649F89, 0x00649FBC, 0x0064A09B). So a plan that unmarks a dead player or monster leaves the cells alone (they are not there, or are the corpse's), a corpse call, a creation and a relocation force the unmark, and an object a plan unmarks needs `HasCollision` set. This reads the `HasCollision` gate path/0005 O1 states at 0x00649611 and adds the override at 0x0064961A. (0x00649560–0x00649758, fn:UNIT_CollUnmark@0x00649560, `r70-xrefscan2.txt`)
- [I] **3. `0x00650590(path)` snaps the path's point to the middle of its tile and re-checks the room; it marks nothing.** It takes the path in `EAX` and the stack (`stdcall`, `ret 4`): `x = (path.x & 0xFFFF0000) + 0x8000`, `y` likewise, then `sub_0064FB90_PathSetPoint(path, x, y, 0)` (0x00650590–0x006505BD). `PathSetPoint` stores the point (`+0x00`, `+0x04`), recomputes the sub-tile fields `+0x08`, `+0x0C` (`>> 11`, 0x00643290) and, when the path has its unit and flag 1, calls `sub_0064FAD0_PathRoomUpdate`, which does nothing while the point's whole coordinates (`+0x02`, `+0x06`) are inside the current room's rectangle and otherwise looks the room up (`sub_00463740_RoomAtSubtile`), unlinks and relinks the unit (`UnitRoomUnlink`, `RoomUnitAddMarked`, `UnitMarkUpdated`, 0x0064FB62–0x0064FB7A). The "marked" of `RoomUnitAddMarked` is the unit-list mark of the frame, not a grid mark; no call to `UNIT_CollMark`, `UNIT_CollUnmark`, `COLL_PatternMark` or a `COLL_*Or`/`Clear` is made by these four functions. So `UnitCorpseColl`'s last call (0x00649FAA, 0x00649FDE) changes only the fraction of the corpse's position to one half, which leaves the whole coordinates the 3×3 or the plus was just written around, so it neither moves the cells nor, in practice, the room (a room change needs a point outside the rectangle the unit was in). Named `sub_00650590_PathSnapToTileCentre`. Not followed: the three room-list callees and `0x00643290`. (0x00650590, 0x0064FB90–0x0064FC10, 0x0064FAD0–0x0064FB84, fn:sub_0064FB90_PathSetPoint@0x0064FB90, fn:sub_0064FAD0_PathRoomUpdate@0x0064FAD0)
- [I] **4. A revived monster is re-marked by the revive routines; nothing in them clears the 3×3.** `UnitReviveColl` (0x00649FF0) acts only at path mask `0x8000` (0x0064A037) and its two callers are client code (0x004AEEDC, 0x004AFFA8), so a server corpse, which keeps mask `0x100` (path/0005 C4), does not meet it. The server routine read is `sub_005CC960_MonReviveInPlace` (self-resurrect, start 61; Resurrect, do 97, 0x005CCBF5): for a monster with a room it sets mask `0x100` (`PATH_SetMarkMask`, 0x005CC9EA), runs `sub_00649CA0_PathPatternRefresh` (0x005CC9F0: `UNIT_CollUnmark(unit, 1)`, pattern from size into `path+0x48`, `UNIT_CollMark`) and then `COLL_PatternMark` with the pattern `path+0x48` and `0x100` as its last argument (0x005CCA68). `sub_005C07A0_SkillReviveDo` and `sub_005C56C0_SkillDo58Revive` also call `PathPatternRefresh` (0x005C0953, 0x005C5898). **Not found:** `sub_005A7C20_MonSetMode` calls `UNIT_CollMark` at 0x005A7CB1 only when `sub_005541B0_UnitIsDead` is 0 at 0x005A7CAC, before its handler call (0x005A7D67); where the mode word is written was not located, so whether a dead-to-alive mode set meets that test as alive or dead is not stated, and `MonSetMode` is not given as a route. No routine read calls a clear with `0x8000`: the direct callers of `COLL_RectClearWH` are `UNIT_CollUnmarkRect` (0x006238B0) and `UNIT_CollUnmark`'s object branch (0x0064969A), and the pattern unmarks are reached with the unit's own mask. So the corpse's 3×3 of `0x8000` stays after a revival by these routes, as C4 says for the corpse. Not followed: `MERC_Resurrect`, `sub_005F99A0_AiFetishReviveCb`, `sub_0054C0E0_Pkt41Resurrect`, `sub_005C3350_SkillSt21Revive`, and the callees of the revive routines (`0x00573780`, `0x00547E90`, `0x00545CD0`). (fn:sub_005CC960_MonReviveInPlace@0x005CC960, fn:sub_00649CA0_PathPatternRefresh@0x00649CA0, fn:sub_00649FF0_UnitReviveColl@0x00649FF0, fn:COLL_PatternMark@0x0064EA90, fn:sub_005A7C20_MonSetMode@0x005A7C20, `r70-xrefscan3.txt`)
- [I] **5. Whether the 3×3 is a mask nothing tests.** Among the immediates that reach a path's move mask through `sub_00648CE0_PathSetCollMask` (19 direct calls with an immediate push) or a store at `+0x50` (34 immediate stores, most in unrelated records), none has bit `0x8000` (0 of 53). The monsters' masks `0x1804`, `0x3401`, `0x3C01`, `0x0804` and the spawn masks have no such bit either. Not seen: a mask built in a register or read from a table. (0x00648CE0, `r70-collmask.txt`)
- [I] **6. `unflatDead` (`+0x006` bit 4) has one reader, and it is a client draw test.** `sub_004638A0_MonStats2FlagTest(class, 0x14)` (the byte `+4 + (0x14 >> 3)`, bit `0x14 & 7`) has one direct call with that index, at 0x004648AB, in the function at 0x00464860 (named `sub_00464860_UnitFlatDrawTest`), a per-unit-type predicate whose monster case (0x004648A3–0x004648BF) returns 1 only for a monster in mode 12 whose `unflatDead` is 0. That function has one direct call, 0x004DDAD6, in a client loop over a room's unit list (the head at 0x004DDA41, the cell record at stride `0x24`), where a unit for which it returns 1, or whose `+0xC4` bit 20 is set, is appended to a draw list at `ebx + 0xEA64` (max `0xBB8` entries) by `0x004DD600`, and any other unit goes through `0x004DCFA0` (and `0x004DD6E0` when `+0xC8` bit 7 is set). Those three callees call only the path position getters (`PathGetX`, `PathGetY`). So the bit decides which draw-list routine a dead monster is entered through; it changes no grid mark and no move mask, and the server never reads it. Of the 11 register-form calls of the getter, 10 load `EDX` as a constant plus a register the preceding test fixes (indices 2, 7, 8, 12) and one is `deadCol`'s (index 0x13); `deadCol` has the four direct tests below. (0x004648AB, 0x004DDAD6, `r70-flagtest-sites.txt`, `r70-xrefscan2.txt`)

The four direct `deadCol` tests of the image (index 0x13): `SUnitCreate` 0x00555481, `MonDeathCorpseMark` 0x005A65CD, `sub_0057AF00` (a getter returning 1 when the bit is 0; no direct or absolute reference to it in the image, 0x0057AF16) and `COMBAT_ApplyCold` 0x0057B138 (`EDX = ESI + 0x13` with `ESI` zeroed at 0x0057B109). `UnitRelocate` (item 1) has none.
