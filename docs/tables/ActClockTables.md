# ActClockTables: the act light clock's three tables (`Game.exe` image)

> **Source:** the pinned `Game.exe` image (no excel file)   **Tables:** 3, 18 rows (54 dwords): 42 values listed, 12 by two rules   **Records:** six rows of three dwords
> **Doc status:** address, row layout and reader of each table; the values listed or given by a rule that the survey checks against the image ([ADR-0031](../adrs/0031-constants-of-the-code-image.md));
> the meanings taken from [frame/0001 § 3.1](../findings/frame/0001-tick-and-messages.md#31-actsclockpass-the-act-light-clock) with its tags
> (plan 0063 Phase 1, entry `2026-11-04-spec-writer-archivist-act-clock-tables`)

## Purpose

`ActClockTick` (0x0061C040) steps each act's light clock against three small constant tables. No MPQ file holds them and they are not an excel table:
they are constants of the code, so this doc sits beside [PathDirTables](PathDirTables.md) and [PathTypes](PathTypes.md), the other image-constant docs of
`docs/tables/`, and not under `docs/formats/` (no file format is described). The reader is [sim/frame § G1b](../specs/sim/frame.md#g-the-other-per-frame-passes);
the step that uses them is frame/0001 § 3.1. Generated and checked by `python3 -I tools/actclock_survey.py summary|md <game.exe>` (gate survey `actclock`).

## Layout

- `[C]` The three tables are contiguous in the image's data: `g_ActClockTable0` at `0x007443F0`, `g_ActClockTable1` at `0x00744438`, `g_ActClockTable2` at `0x00744480`
  (re/symbols.csv), 72 bytes each, the next at the address that follows (`0x007443F0 + 72 = 0x00744438`, `+ 72 = 0x00744480`; `0x00744480 + 72 = 0x007444C8`).
  Each is six rows of three little-endian dwords: **`start`** (offset 0), **`type`** (offset 4), **colour word** (offset 8). Row `p` is at `table + 12 p`.
- `[I]` Readers (frame/0001 § 3.1, "the xrefs to them are reads only"): `ActClockTick` and `ClockStep` (0x0061BEE0) read `start` and `type`, and 0x0061BCE0 blends two
  rows' colour bytes into `+0x18..+0x1A` of the clock. Which table the step reads depends on the clock's flag word `f` (`+0x30`) and the act index `a`:
  - when `f` is 0, the next row's `start` (times the clock's scale `k`) is compared against table 0, and the new `type` and `start` are taken from table 0, which is also
    the table whose `type == 2` adds to the counter;
  - when `f` is set, the compare reads table 1 in act index 3 and table 2 otherwise, and the new `type` and `start` are taken from table 2 in every act (so table 1's
    `type` column is never read by that step).

  The exact step is the `[C]` block of frame/0001 § 3.1 (0x0061BF4F–0x0061BFA7).
- `[C]` The colour word is below `0x01000000` in all 18 rows (its top byte is 0), and every `type` is 0 to 3 (the rows below, checked by the survey).
  `[I]` With the three bytes 0x0061BCE0 blends, the colour word is a three-byte colour (frame/0001 § 3.1); the channel order is an open question.
- `[I]` `start` is in the units of the clock's `c` counter over `k` (`c` is reset at `k * 360`; the largest `start` is 350). frame/0001 § 3.1 tests `type == 2` in table 0 and
  copies `type` into `v` (`+0x04`); what a `type` value means to the client is an open question.

## Values

Rows are `(table, p, start, type, colour word)`. Table 2's `start` column and table 1's `type` column are given by the rules below, not listed (ADR-0031). The values are generated by `actclock_survey.py md`, and the survey compares these rows with the image.

- `[C]` **Rule, table 2's `start`:** `start(p) = 60 * ((p + 5) mod 6)`, that is 300, 0, 60, 120, 180, 240 for `p` = 0..5. It equals the image's six values (survey key `t2_start_rule_mismatches=0`); it is no claim about how the table was made.
- `[C]` **Rule, table 1's `type`:** `T1[p].type = T0[p].type` for `p` = 0..5 (survey key `t1_type_rule_mismatches=0`); an equality on the pinned image, no claim about how the table was made.
- No rule is known for the other 42 values, which are listed above: the `start` columns of tables 0 and 1 (not sorted by row), the `type` columns of tables 0 and 2, and every
  colour word. Table 2's colour words are `0xF31E00` except rows 1 and 4 (`0xF41E00`), a description by cases, which ADR-0031 does not count as a rule.

## Survey

`python3 -I tools/actclock_survey.py summary workspace/install/app/game.exe` prints `SURVEY actclock`: tables 3, rows 18, a crc32 of each table's 18 dwords, each rule's mismatches, and `doc_missing` and `doc_mismatches` (the 18 rows above against the image). It exits 1 on any mismatch and is baselined in `tools/gate/baselines/actclock.txt`.

## Open questions

- `[L]` The colour word's channel order: which of its three bytes is red, green or blue (frame/0001 § 3.1 reads the blend at 0x0061BCE0 into `+0x18..+0x1A`, not the client's use of them).
- `[L]` What a `type` value (0 to 3) means to the client; frame/0001 § 3.1 reads only the server step's `type == 2` test and the copy into `v`.
